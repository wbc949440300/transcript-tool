## 账号池运营能力 + 代理池（2026-10-31）

> 目标场景：**抖音多号跑量** + **快手大量跑量**（快手不需要账号池，它要的是出口池）。
> 小红书暂不跑量，不涉及。

---

### 1. 账号池（以抖音为主）

#### 1.1 已有能力（本轮之前就绪）
- `cookies/douyin/account_*.txt` 多号轮换（`login_cookie.py douyin --account account_1` 一步生成）
- 每个号**独立浏览器 profile**（`douyin_account_1`），登录态互不串
- 账号级冷却（风控失败只罚那个号 15 分钟，不停整个平台）

#### 1.2 本轮新增

| 能力 | 说明 |
|---|---|
| **账号级计量** | 选中即记「今天用了多少」（`cookies/.accounts.json`，按自然日滚动）。**单文件 cookie（`cookies/douyin.txt`）也记账**——这条曾经漏掉，已修 |
| **健康度** | 每个号的累计成功/失败、成功率、最近一次失败原因与时间；风控失败时记账 |
| **选择策略（升级）** | 旧版是"索引轮询" → 现在：**跳过冷却 → 今天用得最少的 → 成功率最高的**。选中立刻 +1，所以即使指标打平也会自动在两个号之间来回 |
| **页面可见** | `/risk/status` 每个平台带 `accounts: [{name, usedToday, ok, fail, successRate, cooling, lastFail}]` |

#### 1.3 记账触发点
- 抖音专用通道（`douyin.py`）：抓取成功记 ok；命中风控/人机校验记 fail（带原因）
- yt-dlp 通用通道（`extractor._extract_info`）：带 cookie 的尝试才记账（B站/TikTok 等）
- 匿名抓取**不记账**（本来就是"没有动账号"）

### 2. 代理池

#### 2.1 配置

```
TRANSCRIPT_PROXY_POOL=host1:8080,host2:8080             # 全局池
TRANSCRIPT_PROXY_POOL_KUAISHOU=host1:8080,host2:8080    # 平台单独一个池
TRANSCRIPT_PROXY_DOUYIN=socks5://127.0.0.1:1080         # 单条（等效"只有一条的池"）
TRANSCRIPT_PROXY_MEDIA=…                                # 只给媒体 CDN（默认直连省流量）
```

优先级：平台池 > 全局池 > 单条平台代理 > 单条全局代理 → 都没有就是直连。

#### 2.2 关键行为

| 行为 | 说明 |
|---|---|
| **账号↔出口稳定绑定** | 同一个号（或匿名 `anon`）**始终走同一条出口**（crc32 绑定，跨进程稳定）。避免"同一个号一会儿从 A 出口、一会儿从 B 出口" |
| **无账号时轮换** | 快手这类没有账号概念的，按请求轮询池子，把量摊到多条出口上 |
| **出口级冷却** | 冷却/限流记录在 `platform:<平台>@proxy:<出口>` 上：一条出口被限流，**其他出口照常用**；`pick_proxy_available()` 会主动跳过冷却中的出口 |
| **登录同出口** | `login_cookie.py` 新增 `--proxy`，并默认自动取"与抓取端同一条出口"——否则"登录地在 A、抓取地在 B"本身就是异常信号 |
| **展示脱敏** | `/risk/status` 里只显示 `协议://***@host:port`，不泄露代理账号密码 |

### 3. 实测与测试

- 真实抖音任务（改完重跑）：**SUCCESS / 口播 1164 字 + 画面文字 1145 字** —— 抓取链路重构后主流程未受影响
- 真实 `cookies/` 记账：`pick_account` → `usedToday 1`；记一次成功 → `ok 1 / successRate 1.0`；`/risk/status` 正确显示
- `pytest`：**224 项全过**（新增 14 项：用量均衡、冷却跳过、健康度排序、单文件回退记账、池的绑定/轮换/优先级、出口级冷却隔离、脱敏）

### 4. 还没做（等你出面）

- **买代理**：代码全通，`.env` 里还没有任何 `TRANSCRIPT_PROXY*`
- **登号**：`python login_cookie.py douyin --account account_1`（要扫码）；池子放 2~3 个号
- 之后：`/risk/status` 就能看到每个号今天跑了多少、谁被冷却了

> 顺序建议：先配代理（出口多样性），再登多号——同一 IP 上挂多个号，平台很容易把它们关联起来。

## 账号登录页（2026-10-31）

> 需求：给"登录各平台账号"做一个页面，别让人敲命令行。
> 定位：**本机桌面功能** —— 登录必须弹浏览器窗口人工扫码/输密码，所以只在有桌面的机器上有意义
> （不做、也不打算做"云端导入凭据"那条路）。

---

### 1. 页面长什么样

顶部导航新增「账号」入口（`#/accounts`），页面上按平台列出账号：

```
抖音    已登录 1 个                      [登录默认账号] [+ 新账号 account_1]
  （默认）  ● 已登录 2026-10-30 15:42（1 天前）   _browser_profile_douyin      [重新登录] [验证]
快手    未登录 · 匿名即可，无需登录          [登录默认账号] [+ 新账号 account_1]
  （默认）  ○ 未登录                        _browser_profile_kuaishou    [登录]
小红书  已登录 1 个 ...
B站     未登录 ...

[打开 cookies 文件夹] [刷新状态]
```

- 登录中会显示"登录中…（请到浏览器窗口完成）"，页面最多每 5 秒刷一次、等 5 分钟
- 「验证」会**无窗口**地跑一次 `login_cookie.py --check`（能发现登录态过期并顺带刷新 cookie）
- 账号冷却（被平台限过的号）也直接显示在行上

### 2. 后端（4 个接口，`/prod-api` 前缀）

| 接口 | 作用 |
|---|---|
| `GET /login/status` | 各平台账号状态（纯读本地文件：cookie 是否存在/多久前登录/profile 目录/账号冷却）——**不联网、不开浏览器** |
| `POST /login/start {platform, account}` | 拉起 `login_cookie.py`（弹浏览器窗口，人工登录）；**同一账号不会重复启动**（防弹两个窗口） |
| `POST /login/check {platform, account}` | 跑 `--check` 验证登录态，把脚本输出带回来 |
| `POST /login/open-dir` | 打开 `cookies/` 文件夹 |

实现放在 `app/account_login.py`，接口在 `app/api.py`。

### 3. 两个必须守住的点

1. **命名必须与抓取端一致**：`account_login._profile_dir()` 直接调用
   `login_cookie._profile_for()`（单一事实来源），避免重演今天修过的
   "登录用 A profile、抓取读 B profile → 登录态白登"。
2. **不做自动登录**：必须人工完成；接口也只是"拉起窗口"，不碰账号密码。

### 4. 顺手修的两个小问题

| 问题 | 影响 | 处理 |
|---|---|---|
| 后端用半角 `(默认)`、前端用全角 `（默认）` | 前端会把"默认账号"当成一个普通账号名传回后端 → 参数非法 | 统一成全角 `（默认）` |
| `file` 字段用 `str(Path)` | Windows 上是反斜杠，前端显示不统一 | 改 `.as_posix()` → 一律 `douyin/account_1.txt` |

### 5. 验证

- `pytest`：**282 项全过**；本页新增 7 项（状态读取含默认行与账号池、profile 命名、登录时间、
  参数校验、防重复启动、`--check` 结果映射、账号冷却可见）
- 真实接口（服务重启后）：
  ```
  抖音   已登录 1 | （默认）:✓
  快手   已登录 0 | （默认）:✗
  小红书  已登录 1 | （默认）:✓
  B站    已登录 0 | （默认）:✗
  ```
- 前端脚本 `node --check` 通过；页面已含账号视图

### 6. 分发到别的电脑时（配合"打包"那条注意事项）

**不要拷贝 `cookies/` 目录**：每台机器各自点「账号」页登录自己的号，**一个账号只在一台机器上用**。
页面「说明」卡里也写了这条。
