# 三平台专项：抖音 / 快手 / 视频号

> 2026-10-31 · 基于当前代码 + 本次实测探测（抖音分享页 1 次、快手分享页 1 次、快手通道直调 1 次）
> 目的：把"平台提取"这件事按平台拆开，给出各自的矛盾点、已证实的事实、处理方案与取舍。

---

## 0. 一句话结论

| 平台 | 真正的矛盾 | 现在做得怎么样 |
|---|---|---|
| **抖音** | 唯一必须"过风控"的平台：每次任务要开一个真实浏览器页面，还要下全片视频做 ASR | 能跑，但指纹每任务都变、风控判定靠页面文本、下载不分码率 |
| **快手** | 最轻最稳：1 次 GET 就能拿全（标题/作者/时长/6 条直链） | 稳定，但解析靠正则、下载请求头不完整、图集作品会误报"链接失效" |
| **视频号** | **没有平台抓取**，风险全在本地：系统代理被改 + 根证书 + 第三方 MITM 二进制 | 链路已通，但默认自启 MITM 工具、退出不还原代理 |

## 1. 本次实测到的事实（不是推测）

### 1.1 抖音：SSR 分享页已经拿不到视频数据了

探测 `https://www.iesdouyin.com/share/video/<id>/`（移动 UA）：

```
HTTP 200 · 32KB · final 未跳验证页
_ROUTER_DATA 存在
loaderData = { "video_layout": null, "video_(id)/page": {...} }
"video_(id)/page" 的键只有：ua / isSpider / query / renderInSSR / lastPath / appName / host / itemId / isVideoOptimize
→ 没有 aweme_detail、没有 play_addr、没有 bit_rate、没有 item_list
```

**结论：**
- "用 SSR 分享页替代无头浏览器"这条路**已经走不通**（`renderInSSR: 1` 但数据是客户端再拉的），不要再花时间。
- 但 `loaderData["video_(id)/page"].itemId` 是**现成的**，短链解析可以少一次跳转。
- 页面里**永远**包含 `captcha` / `verifyCenter` 这些 SDK 字样（本次实测两处都是脚本引用，不是验证页）。
  → **绝不能把 `captcha`/`verify` 当页面风控特征**，否则每个正常页面都会被判成风控。
  当前 `douyin.py` 用的是中文特征（验证码/滑块/安全验证/访问频繁）+ detail API 的 HTTP 状态，方向是对的，**保持**。

### 1.2 快手：现行解析方式仍然成立，但确实没有结构化 JSON

探测 `https://m.gifshow.com/fw/photo/3x5gu3rc5sqd9ni`：

```
HTTP 200 · 163KB · 未跳验证码
__APOLLO_STATE__: 无 · __INITIAL_STATE__: 无
"caption": 有 · "userName": 有 · .mp4 直链: 1 条
```

直调 `fetch_kuaishou()`（改后代码）：**1.0s 成功**，标题/作者/时长 54s/6 条直链全部正常。

**结论：**
- 快手不需要浏览器、不需要登录，是三个平台里成本最低的。**不要为了统一而把它改成 Playwright。**
- 因为没有结构化 JSON，正则就是唯一手段 → 要防的是"页面改版后静默解析出半截数据"。

### 1.3 视频号：`_restore_proxy()` 只在 `stop()` 里调用

`app/external_dl.py` 全文只有一处调用 `_restore_proxy()`（`stop()` 内），**没有 atexit / signal / 异常兜底**。

→ 服务被 `taskkill /F`、崩溃、断电时，系统代理会留在 `127.0.0.1:2023`。
→ 下载器若同时没起来（被杀软拦、证书失效），**全机断网**，而用户不知道原因。

## 2. 抖音专项

### 2.1 成本结构（每次任务实际发生什么）

| 步骤 | 现状 | 代价 |
|---|---|---|
| 打开视频页 | `p.chromium.launch(headless=True)` + `new_context(user_agent=固定UA)`，**每任务全新实例** | 启动 1~2s + 页面加载几十个静态资源请求 |
| 拦截详情 | `aweme/v1/web/aweme/detail` 响应 | 1 次 API |
| 拿文案 | 无真字幕 → 下载**整条视频**（`play_addr.url_list[0]`，通常是最清晰的那条） | 100MB~400MB/条（长视频） |
| 转写 | GPU whisper medium | 4 分钟视频约 36s（实测） |
| 预览 | 直接用平台直链 | **几小时后失效** |

### 2.3 已实施（抖音组，2026-10-31）

| 项 | 落地情况 |
|---|---|
| **持久 profile + 固定指纹** | `app/browser.py::open_profile()` 支持 `profile_dir/locale/timezone/viewport/stealth/proxy`；抖音走 `profile_dir_for("douyin")` = `cookies/_browser_profile_douyin`，固定 UA + `--disable-blink-features=AutomationControlled`。实测：跨进程复用（文件数 766→771、写入时间更新），抓取 3.3s。 |
| **登录态打通（本轮补的关键缺口）** | 之前 `login_cookie.py` 只写共用的 `cookies/_browser_profile`，而抖音抓取读 `_browser_profile_douyin` —— **登录与抓取是两个浏览器，登录态白登**。现在 `login_cookie.py` 按平台取同一目录：`python login_cookie.py douyin` 直接写进抓取用的那个 profile。 |
| **每账号一个 profile** | 新增 `--account account_1`：登录态存 `_browser_profile_douyin_account_1`、cookie 导出 `cookies/douyin/account_1.txt`；抓取端按同一命名规则取用（`_profile_name_for()`）。多账号登录态互不串，也避免了"一条出口被限流 = 整平台停摆"。两者命名一致性已用单测确认。 |
| **最低码率下载** | `douyin.py` 返回全部 26 档变体（码率/gear/分辨率）；ASR 取最小档、预览取最大档。**实测踩坑**：低码率档直链下到的文件 ffprobe 读不出任何流（4.6MB/5.9MB 两档皆如此）→ 加了"候选验证 + 换下一档"与自适应记忆（本进程确认不可用后直接走默认档）。净效果：没省到流量，但把一条会硬崩的链路（`IndexError: tuple index out of range`）变成可回退链路。 |
| **刷新直链** | `POST /transcript/refreshMedia`（只重取详情、不重跑转写，用 `platforms.adapter_for()` 分发）+ 前端结果卡「刷新直链」按钮（仅抖音/快手）+ `MEDIA_TICK` 缓存穿透。实测：刷新 26 条直链、库内首链更新。 |
| **图集识别** | `aweme_detail.images[]` → `_ocr_images()`（与小红书图文共用），不再落到"抖音视频下载失败"。 |

> 维护提示：`cookies/_browser_profile*` 每个目录会随使用增长（当前抖音 53MB、小红书共用 331MB）；
> 删掉目录即可重置指纹与登录态（下次抓取会重建一个全新的）。

### 2.2 方案（供对照）

**① 浏览器复用 + 指纹一致（收益最大，风险最低）**
- 现状：每个任务 `launch()` 一次，全新 profile → `navigator.webdriver=true`、无历史、无插件、语言/时区/分辨率全默认、UA 硬编码 Chrome 120。
- 做法：照搬 `browser.py` 的 `launch_persistent_context`（`cookies/_browser_profile_douyin`），加
  `--disable-blink-features=AutomationControlled`、`locale="zh-CN"`、`timezone_id="Asia/Shanghai"`、
  viewport 固定一档；**一个账号一个 profile**，有 cookie 时直接用该 profile 登录态。
- 效果：同一账号在平台侧看到的是"同一台机器、同一个浏览器"，而不是"每次一个新浏览器"。
- 代价：每账号约 100~200MB 磁盘；批量时进程常驻。

**② ASR 下载选最低码率（省带宽、少耗时，不影响文案）**
- `aweme_detail.video.bit_rate[]` 里每档都有 `play_addr` 和 `bit_rate` 数值。
- 现状：`play_addr.url_list[0]` 或 `bit_rate[0]` —— **没有按码率挑**，拿到哪档算哪档。
- 做法：**ASR 用最小 `bit_rate` 的那档**（480p 级，语音足够），**预览用最大档**；
  直链下载失败时按 `url_list` 依次换 CDN 主机（现在只试第一条就落到 yt-dlp 重试）。

**③ 风控判定用 API 状态，不用页面文本**
- 现状：页面文本特征 + `resp.status` ∈ {401,403,429}。
- 补充：抖音详情接口在风控时通常返回 `status_code`（JSON 内）或空 body + 验证页跳转；
  建议把 `body.status_code`（非 0）也纳入判定，并记录到日志/`/risk/status` 的 reason。
- **不要**加 `captcha`/`verify` 文本特征（见 §1.1）。

**④ 直链过期 → "刷新直链"而不是重跑整条任务**
- 抖音直链几小时过期，历史里的预览会黑屏（HANDOFF §6.8 已记录）。
- 做法：详情页/历史页给一个"刷新直链"按钮 → 只重新取一次 `aweme_detail`（1 次页面访问），
  更新 `videoUrlList`，**不重跑 ASR**。
- 不建议给所有任务都存本地 mp4：20 条 × 100MB+ 会撑爆磁盘（已有保留策略在删）。

**⑤ 抖音图集/图文作品（当前会报错成"下载失败"）**
- `aweme_detail` 对图文作品给的是 `images[]` 而不是 `video`。
- 现状：`title` 有值 → 不算失败 → 没有 `video_url` → yt-dlp 兜底 → 最终报"抖音视频下载失败"。
- 做法：检测 `images` → 走"取图 + RapidOCR"（复用小红书图文那套），或至少给出明确提示
  "这是图文/图集作品，暂不支持视频转写"。

**⑥ 明确不做**
- 自研 `a_bogus` / `X-Bogus` 签名直接打详情 API：军备竞赛、随时失效，收益不如①。
- 移动端 `m.douyin.com` 抓包逆向：同属签名问题。

## 3. 快手专项

### 3.1 现状评价

`m.gifshow.com/fw/photo/<id>` 是**服务端渲染的分享页**，1 次 GET、无登录、无需签名 —— 这是目前最健康的抓取路径。
实测 1.0s 拿到：标题 42 字、作者、时长 54s、6 条 mp4 直链。

### 3.2 方案

**① 解析加固（防页面改版静默出错）**
- 现在用正则抓 `"caption"` / `"userName"` / `"duration"` / `.mp4`。
- 加"结构变化告警"：如果**有 mp4 但 caption 为空**、或 `duration` 解析不到，日志 WARN 并带上页面指纹
  （长度 + 关键键命中情况），便于改版后第一时间发现，而不是用户报"文案是空的"。
- 如果哪天页面出现结构化 JSON（`window.__XXX = {...}`），优先解析 JSON、正则做兜底。

**② 下载请求头补全**
- `extractor._download_http_media()` 现在用**桌面 Chrome UA、无 Referer** 直接拉 `ndcimgs.com` 直链。
- 快手 CDN 对部分链接会挑 UA/Referer：建议按平台传移动 UA + `Referer: https://m.gifshow.com/`。
- 直链有 6 条（`video_urls`）：失败时依次换，不要直接落到 yt-dlp 的 3 次重试。

**③ 风控信号补一个**
- 模块注释里提到 `www.kuaishou.com` 会返回 `{"result":2}`；分享页也可能返回 JSON 而不是 HTML。
- 建议：响应以 `{` 开头且含 `"result":2` / 空 body → 判 risk（现在只看中文标记 + 长度 < 5000）。
- 长度 < 5000 但无风控标记 → 保持"不冷却、原样重试一次"（已改）。

**④ 快手图集作品**
- `fw/photo/<id>` 对图文作品没有 mp4 → 现在报"未解析到内容（链接可能已失效）"，会误导用户。
- 建议同抖音：检测 `photoType`/无 mp4 但有图片 → 明确提示或走 OCR。

**⑤ 明确不做**
- 不要给快手加 cookie 依赖：分享页匿名就够，加 cookie 只会平白暴露账号（`TRANSCRIPT_COOKIE_MODE=fallback` 已保证只在 login 信号时用）。

## 4. 视频号专项

### 4.1 先摆正定位

视频号**没有可抓的网页接口**（HANDOFF §6.7、§4.1 已确认：`finder-preview/api/feed/get_feed_info` 只有描述/作者/封面/点赞，没有视频流）。
所以它的"风控"问题不是平台风控，而是**本地 MITM 的稳定性和副作用**。

### 4.3 已实施（2026-10-31 当天完成）

| 项 | 落地情况 |
|---|---|
| **默认不自启** | `TRANSCRIPT_EXT_DL_AUTOSTART` 默认由 `1` 改为 `0`：服务启动不再拉起下载器、也不再自动下载安装包；用视频号时在页面上点一次「启动下载器」。`app/main.py` |
| **启动体检** | 新增 `external_dl.sanity_check_proxy()`：系统代理指向本机 MITM 但下载器不在线 → 还原启动前备份（没有备份就关闭代理）。每次服务启动自动跑，日志写 app.log。实测：代理指向 clash 7890 时正确"不干预"。 |
| **退出还原** | 新增 `external_dl.shutdown_cleanup()`：本进程拉起的下载器会被停掉（`allow_elevate=False`，**退出时不弹 UAC**）；不是我们拉起的，只要代理仍指向 MITM 也照样还原；两台钩子（FastAPI `shutdown` 事件 + `atexit`）都登记、幂等。打桩 7 例 + 真实调用 1 例全通过，注册表核对未被误改。 |
| **页面可见** | `/ext/status` 新增 `system_proxy`（含 `enable / server / is_mitm / active_mitm`）；在线但代理未指向本机 → 橙色提示；离线但代理残留 → 红色告警 + 「还原系统代理」按钮（新端点 `POST /ext/proxy/restore`）。 |

**实测发现一个当前状态问题**：此刻下载器在线，但系统代理是 `127.0.0.1:7890`（clash），
不是 `127.0.0.1:2023` —— 也就是说**微信里现在不会出现注入的下载按钮**。
以前这个状态在页面看不出来；现在状态卡会直接显示"系统代理未指向本机（微信里的下载按钮不会注入）"。

### 4.2 方案（供对照）

**① 默认不自启 MITM 下载器（建议改默认值）**
- 现状：`TRANSCRIPT_EXT_DL_AUTOSTART` 默认 `1` → 服务一启动就拉起 `wx_video_download.exe`，
  它会把**系统代理**改成 `127.0.0.1:2023`（全机流量走 MITM）。
- 风险：用户只是打开工具转个本地文件，也把全机网络挂到 MITM 上；下载器一挂 = 全机断网。
- 建议：默认 `0`；只在用户打开"视频号"页或点"一键启动"时启动；页面上明确提示"运行期间系统代理会指向本机"。

**② 启动体检 + 退出还原（补当前缺口）**
- 现状：`_restore_proxy()` 只在 `stop()` 调用（本次确认）。
- 加三处：
  1. 服务启动时：若 `ProxyServer` 指向 `127.0.0.1:2023` 但下载器不在线 → 还原备份或关闭代理；
  2. 进程退出时（`atexit` + `signal`）→ 调 `stop()`/`_restore_proxy()`；
  3. `/ext/status` 里同时返回"当前系统代理"和"是否指向本机 MITM"，让用户一眼看到。
- 这三条是**防止用户断网**的兜底，优先级高于任何抓取优化。

**③ 用 `get_feed_info` 补元数据（把"文件名当标题"换掉）**
- 用户粘贴视频号链接时（现在直接拒绝），可以调 1 次 `finder-preview/api/feed/get_feed_info`
  拿到描述/作者/封面/点赞，展示出来并提示"请在微信里播放并点下载"。
- 下载完成后，watch_folder 用 `标题_时长` 命名/归档，而不是下载器的文件名（含平台前缀、重复后缀）。
- 注意：这是非公开接口，只做"用户主动粘贴时 1 次"，不要轮询。

**④ 去重与命名**
- 下载器会重复下载同一视频（同一标题多份）；watch_folder 现在按"路径+大小+mtime"记忆。
- 建议加一层内容去重：标题 + 时长（ffprobe）+ 文件大小，命中则跳过转写，直接复用历史记录。

**⑤ 长视频的期望管理**
- 实测 29.7 分钟 → 6.5 分钟（GPU medium）。这是 ASR 的物理下限（约 4.5x 实时）。
- 建议：任务状态里显示"预计还需 X 分钟"（按已有时长/速度估算），避免用户以为卡死；
  不建议为长视频降模型（small 会明显掉字）。

**⑥ 供应链**
- 下载器是第三方闭源二进制（GitHub release，safe 版，有 checksums 时校验 SHA256）。
- 建议：固定版本号 + 记录来源与哈希到日志；**不要自动升级**；首次安装前在页面提示"来自第三方"。

## 5. 三平台统一运行策略（建议值）

| 项 | 抖音 | 快手 | 视频号 |
|---|---|---|---|
| 抓取并发 | 1（已有平台锁） | 1（已有） | 0（不走抓取） |
| 每任务平台请求 | 1 次页面 + 1 次 detail | 1 次 GET | 0 |
| 节流 | 平台桶 3s + 抖动 | 平台桶 3s + 抖动 | — |
| 失败重试 | risk=停手 / login=带 cookie / transient=匿名 1 次 / permanent=不重试（已实现） | 同左 | — |
| 冷却 | 仅真风控，按"平台+出口" | 同左 | — |
| 转写 | GPU medium；下载选最低码率 | 同左 | 同左（长视频显示预计时间） |
| 预览 | 直链 + "刷新直链"按钮 | 直链（较少过期） | 本地文件（永久） |
| 图集 | 检测 `images` → OCR 或明确提示 | 检测无 mp4 → 明确提示 | — |

## 6. 需要你拍板的三个取舍

1. **抖音是否上"每账号一个持久浏览器 profile"？**
   优点：指纹稳定、风控概率明显下降、批量更快（复用实例）。
   代价：每账号 100~200MB 磁盘；需要把 `login_cookie.py` 与抓取用同一个 profile。
2. **视频号下载器是否改成"默认不自启"？**
   推荐是。代价：用户第一次用视频号要多点一次"一键启动"。
3. **是否要"刷新直链"按钮？**
   推荐是。抖音直链几小时过期，这是历史记录里预览黑屏的唯一低成本解。

## 7. 建议实施顺序

1. 视频号：默认不自启 + 启动体检 + 退出还原（防断网，1 小时级改动）
2. 快手：下载请求头 + 结构变化告警 + `result:2` 判定（半天）
