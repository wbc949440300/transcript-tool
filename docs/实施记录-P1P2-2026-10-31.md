### 1. 交付内容

#### 1.1 每平台串行队列（`app/scheduler.py`）
- 同一平台同时只跑 1 个任务；不同平台可并行。
- 队列按平台（通用站点按域名），有上限 `TRANSCRIPT_QUEUE_MAX`（默认 100/平台）。
- 队列满时接口返回 429，并给出中文原因；批量提交前用 `can_accept_many()` 按平台累计判断。
- 空闲 1 秒后工作线程自动退出，下次提交再重建（不会长期占线程）。
- 任务状态会显示"排队中（抖音队列第 N 位）"。

#### 1.2 每日预算 + 熔断（`app/risk.py` + `utils` 冷却升级）
- 预算按"任务条数"计，按自然日滚动，持久化在 `cookies/.budget.json`。
- 默认额度：抖音 150 / 快手 200 / 小红书 100 / B站 200 / TikTok 100 / 通用 200。
- 优先级：`TRANSCRIPT_<PLATFORM>_DAILY_BUDGET` > `TRANSCRIPT_DAILY_BUDGET` > 平台默认。
- 超额直接失败（连浏览器都不打开），文案里带已用/上限与调整方法。
- 熔断：风控失败一次 → 冷却 30 分钟（快手 15 分钟）；连续命中 → **翻倍**（60m → 120m，封顶 2h）。
- 半开探测：平台队列本身串行，冷却到期后的第一条任务就是探测——成功即清零，
  再失败则继续翻倍。
- 冷却键 = `platform:<平台>@<出口>`；出口由代理决定（`direct` 或 `proxy:<地址>`）。

#### 1.3 代理支持（默认直连，显式生效）
- `TRANSCRIPT_PROXY` 全局；`TRANSCRIPT_PROXY_<PLATFORM>` 单平台覆盖（如 `TRANSCRIPT_PROXY_DOUYIN`）。
- `TRANSCRIPT_PROXY_MEDIA` 单独控制媒体 CDN（默认直连，避免大流量走代理）。
- 已贯通：yt-dlp（`_extract_info` 与 `download_media`）、urllib（快手分享页、短链解析、
  小红书图片、字幕下载、媒体代理/封面/OCR URL）、Playwright（抖音/小红书浏览器）。
- 所有平台请求都改用**显式 opener**，不再读系统代理 —— 避免被视频号下载器的 MITM
  （127.0.0.1:2023）绕进去。

#### 1.4 抖音指纹（`browser.open_profile` 重构）
- 抖音改用独立持久 profile：`cookies/_browser_profile_douyin`
  （`TRANSCRIPT_BROWSER_PROFILE_DOUYIN` 可覆盖）。
- 固定 `locale=zh-CN`、`timezone=Asia/Shanghai`、viewport、UA，并带
  `--disable-blink-features=AutomationControlled`。
- 启动失败自动回退一次性上下文（不会因为 profile 被占用而整条通道不可用）。
- 小红书同步迁移到新的 `open_profile` 签名。

#### 1.5 验证码/登录墙停手
- 抖音：`page.url` 命中 `/verify`、`captcha`、`/passport` → 立即判风控、冷却并给出
  "先用普通浏览器完成验证"的提示。
- 注意：抖音页面**永远**带 captcha SDK 字样，所以只看 URL 和接口状态，不看页面文本。

#### 1.6 全局 ASR 锁（顺手修的真问题）
- `file_transcribe` 原来有自己的锁 → "链接任务 + 文件任务"会各拿一把锁同时跑两个模型，
  6GB 显存会 OOM。现在统一用 `extractor._WHISPER_LOCK`。

### 4. 已知边界（有意为之）

1. **队列在内存**：服务重启后排队中的任务会丢（与原有"任务态在内存"一致）。
2. **文件转写不进平台队列**：它不碰平台，只受全局 ASR 锁约束；批量视频仍会串行转写。
3. **媒体默认不走代理**：CDN 流量大；需要时用 `TRANSCRIPT_PROXY_MEDIA` 显式开启。
4. **抖音 profile 与登录 profile 分离**：登录仍用 `login_cookie.py` 导出
   `cookies/douyin.txt`，抓取时注入到抖音 profile。指纹一致性与账号登录态是两件事。
5. **半开探测依赖"每平台串行"**：如果以后把平台并发调到 >1，需要额外的探测锁。

### 2. 抖音图集（图文作品）

- `fetch_douyin` 在 `aweme_detail` 里收集 `images[]`。

### 3. 图文按需 OCR

- 新增共享 `_ocr_images(urls, referer, platform)`：先认前 N 张；之后**连续 3 张几乎没新增文字**才停。
- 默认：前 **3** 张必认；单张新增 < **5** 字算"静默"；最多 **20** 张；每张之间 0.5~0.75s 摩擦。
- 阈值刻意很小：短句风格的图文笔记每张也就十几个字，阈值大了会把正文掐断（实测踩过坑，见 §10）。
- `TRANSCRIPT_IMAGE_OCR_QUIET=0` 表示不提前结束（一路扫到 MAX）。
- 小红书图文与抖音图集共用这套逻辑；`xiaohongshu.fetch_image` 已删除（不再重复实现）。

### 4. 保留策略统一

| 层 | 策略 |
|---|---|
| 历史记录 | 条数上限 `TRANSCRIPT_HISTORY_KEEP`（默认 20）+ 可选天数上限 `TRANSCRIPT_HISTORY_KEEP_DAYS`（默认 0=不按天） |
| 任务媒体 | 单独按天清理 `TRANSCRIPT_MEDIA_KEEP_DAYS`（默认 14，0=不清理）；**只删媒体，保留记录** |
| 文案归档 | `文案输出/` 永不自动删除（长期存档，单一事实来源） |

- `trim(keep, keep_days)` 同时支持两种上限；删记录仍连带删 `tasks/<id>/`。
- 新增 `sweep_old_media(days)`：只清 `video.mp4` 等媒体，记录与文案不受影响。
- 启动时执行 `trim(keep, keep_days)` → `sweep_old_media()` → `sweep_orphan_task_files()`。

### 11. 监听目录支持图片（11:16）

**背景**：抖音图集网页端拿不到数据（见 §10），用户只能从 App 保存图片 → 需要一条"图片 → 文案"的自动通道。

**实现**
- 新模块 `app/image_import.py`：一组图片 → OCR → **一条任务**（一次图集 = 一份文案），临时副本用后即删。
- `watch_folder._scan_once` 区分两类：
  - 媒体文件：逐个转写（原逻辑不变）
  - 图片：**同一轮扫描看到的合成一批**（不同时间丢进来的分属不同批次），按 `mtime + 文件名` 排序保证图集顺序
- 单批上限 **30 张**（超出部分下一轮继续）；`TRANSCRIPT_WATCH_IMAGES=0` 可关闭（默认开）。
- 任务类型 `image-ocr`、平台显示"图片OCR"，结果同样进历史、同样自动归档到 `文案输出/`。
- 未知扩展名（.txt 等）仍被忽略；不管媒体还是图片，都是"稳定且未处理过"才入列（防半截文件）。

**验证**
- 单测 7 项：批量合成一条 / 媒体不受影响 / 可关闭 / 未知扩展名忽略 / OCR 合并与副本清理 / 无文字时报错
- 真实端到端：2 张带中文的截图丢进监听目录 → 自动生成 `图片OCR` 任务、**438 字**、归档一份
- 全量测试 **103 项全过**

### 12. 无口播 / 纯音乐任务的提示（11:24）

**问题**：任务成功但没有任何文字时，界面显示"成功"，历史列表那一行更是显示"(等待中)"，用户不知道发生了什么。

**做法**（后端留痕，三处收尾共用同一句话术）
- 新增 `NO_SPEECH_NOTE`（"没有识别到口播内容（可能是纯音乐 / 无旁白视频）…"）与 `_empty_text_note()`；
  在 `_mark_success`（抖音/快手）、通用流程收尾、文件转写收尾三处写入 `errorMessage`，**状态仍是 SUCCESS**。
  前端无需改动：历史列表本来就会显示该字段，结果卡本来也有兜底文案。
- 实测发现 whisper 在**纯静音**上会幻听（3 秒静音 → 正文 "You"），字数不为 0，于是补了一条保守规则：
  **只对"ASR 产出且 < 5 字"**的情况提示"可能是幻听"；字幕 / 图片路径（没有 `segments`）不参与判断，
  避免把"早安"这类正常短文本误报。
