## 1. 视频号元数据：标题/作者/封面（`app/video_channel.py`）

视频流仍然拿不到（只有微信客户端能播），但**元数据**有公开预览接口可用：

```
POST https://channels.weixin.qq.com/finder-preview/api/feed/get_feed_info
body {"baseReq":{"generalToken":""},"shortUri":"<id>"}
```

做的事情：

1. 用户贴视频号链接时，不再只丢一句"不能解析"——顺带取回**标题/作者/封面**，
   写进提示里给他看，并**记下来**
2. 文件经下载器落到监听目录后，按文件名与新记的标题做匹配（完全一致，或两边都 ≥6 字的包含关系），
   命中就把任务标题/作者/封面换成真的 —— **不再是文件名当标题**
3. 取不到就安静放弃，不影响主流程；响应解析用容错遍历（字段名换过几版）

| 配置 | 说明 |
|---|---|
| `TRANSCRIPT_VC_META` | 记住元数据的文件（默认 `video_channel_meta.json`），只留最近 30 条 |

> ⚠️ **未验证**：手上没有真实的视频号分享链接，`get_feed_info` 的**真实响应结构**没有实测过；
> 解析是容错的（`desc/title/nickname/coverUrl/...`），但字段名要不要调整得拿真链接试一次。
> 链接→shortUri 的解析、记忆/匹配、监听目录应用这三段都有单测覆盖。

## 2. 监听目录重复下载去重（`app/watch_folder.py`）

视频号同一条作品常被下载多次（下载器重试、误点两次），以前会**重复转写**。

- 指纹 = **文件大小 + 时长**（不做全文件哈希：几百 MB 哈希一次要几分钟）
- 命中已转写过的指纹 → 跳过转写、记一条 `skipped_duplicate`、文件移进 `processed/`
- 记录存 `watch_dedupe.json`（只留最近 300 条）

| 配置 | 默认 | 说明 |
|---|---|---|
| `TRANSCRIPT_WATCH_DEDUPE` | 1 | 设 0 关掉去重 |
| `TRANSCRIPT_WATCH_DEDUPE_FILE` | `watch_dedupe.json` | 指纹库路径 |

**实测**：同一份视频用两个文件名先后丢进监听目录 →
第 1 个建任务（`task 7522170541907759508`），第 2 个日志写明
"监听目录跳过重复文件（内容同 task …，不再重复转写）"，`/watch/status` 显示 `processed=1 / skipped_duplicate=1` ✅

## 3. 长视频转写进度（`extractor._transcribe` / `file_transcribe`）

29 分钟视频要转 6.5 分钟，以前状态一直停在"正在转写全片口播…"，用户以为卡死。

- `_transcribe(..., on_progress=)`：每 5 秒回调一次（已处理时长 / 总时长 / 预计剩余）

## 4. LLM 额度失效自动回退（`app/llm_correct.py`）

**起因**：星火的订单/额度失效后接口全返回 `403 11200`，纠错与笔记会**静默失败**
（用户只看到"这次没改动""笔记没要点"）。

- 只有 **额度/授权类**错误（401/403/11200/quota/authorization）才回退；网络抖动照旧原样抛
- 回退目标：`TRANSCRIPT_LLM_FALLBACK_BASE_URL / _API_KEY / _MODEL`（三样齐全才生效）
- 首次判定失效后 **10 分钟内直接用备用**，不再每次白撞一次 403

**实测**：当前星火 403 → 自动切千问 qwen3.8-27b：
- 线上纠错实测：**4.1 秒 / 33 处改动 / 零失败块**，响应里明确回话
  `实际服务模型=qwen3.8-27b，回退=True，配置主模型=spark-x2.6`
  （不这么标的话，界面会显示成主模型名，让人以为星火还活着）
- 超长文案（6852 字 / 9 块）生成笔记：**37.5 秒 / 10360 字 / 42 要点 / 17 金句 / 22 术语**，文末含完整转录
- `/ai/status` 新增 `fallbackModel` 字段；纠错/笔记响应新增 `fallback` 与 `configuredModel`

> ⚠️ 待你处理：**星火额度/订单已失效**（403 11200），需要在控制台重新开通；
> 在那之前所有 AI 调用都会走回退（首次多一次 403 往返，之后 10 分钟内直接用备用）。

### 4.1 星火恢复后的复测（同日稍后）

用户重新授权后实测（key `ak-141f…`，端点切到官方标注的 **`/v2`**）：

| 项 | 结果 |
|---|---|
| v2 连通性 | ✅ 200 |
| 真实纠错（1176 字 / 5 块） | **6.5 秒**，零失败块，25 处改动 |
| 实际服务 | `model=spark-x2.6`、`fallback=False` ← 走的就是星火，没回退 |
| 改动质量 | 力距→力矩、蛋头→弹头、夹脚→夹角、师傅→师父…（与之前 A/B 一致） |

排障结论（供以后参考）：

- **端点**：`OpenAI_Chat` 官方就是 `/v2/chat/completions`（`/v1` 也能用，但 v1 的 `/models`
  对任何 key 都返回 200、不校验，容易误判"key 有效"）
- **错误码**：`403 11200` = "APIKEY 没有对应授权" → 控制台给 key 开模型服务；
  控制台里**新发的 key 生效有延迟**（这次授权后约 10 分钟才通）
- `401 apikey not found` = key 不存在（被删除或复制串了）

### 4.2 官方文档核对与请求体修正（同日稍后）

按控制台文档（`maas.xfyun.cn/doc`）逐条核对后：

| 文档结论 | 我们的处理 |

| `max_tokens` **已废弃**，要求改用 `max_completion_tokens` | ✅ 已改：讯飞端点（`*xf-yun.com*`）用新字段，其它服务商（DashScope 等）保持 `max_tokens`。实测同一调用：新字段 2.7s / 旧字段 8.3s |
| 可选模型：`spark-x2.6` / `spark-x2.6-4b` / `spark-x2.6-preview` / `spark-x2.5` / `spark-x2.5-4b` / `spark-x2.5-1.7b` | 按用户要求固定用 `spark-x2.6` |
| 鉴权：`Authorization: Bearer <APIKey>`、端点 `/v2`、最小体 `{model,messages,stream}` | 与我们实现一致（实测 200） |
| 默认限制：**并发 20 / TPM 100 万**（按 key+模型独立算） | 纠错 4 并发、笔记 3 并发，远低于上限 |
| 错误码：`11200` 未授权 / `11221` 套餐不含该模型 / `429` 限流 | 已纳入失败分类（429 会退避+冷却） |

### 4.3 只用星火，不自动回退（用户要求，2026-10-31）

> 用户明确：**AI 纠错只用 `spark-x2.6`，不要自动切回千问；星火不可用时前端弹出提示即可。**

- `.env` 里的 `TRANSCRIPT_LLM_FALLBACK_*` **注释掉了**（保留文本，需要兜底时去掉注释即可）
- 没有备用模型时，`_post_chat` 不再重试，而是抛出一句**人能看懂的提示**（`_friendly_api_error`）：
  | 原始错误 | 给用户的话 |
  |---|---|
  | 403 / 11200 | "AI 模型不可用：该 API Key 没有对应模型的授权（11200）。请到讯飞 MaaS 控制台确认这个 key 已开通/授权 spark-x2.6，或更换 key。" |
  | 11221 | "当前套餐不包含该模型（11221）。请改用套餐内模型或升级套餐。" |
  | 401 / apikey not found | "AI 模型不可用：API Key 无效（平台查不到这个 key）。请核对 .env 里的 TRANSCRIPT_LLM_API_KEY…" |
  | 429 / 11201-11210 | "AI 调用被限流了。稍等一会儿再试…" |
  | 其它 | 原样透传（不掩盖真实错误） |
- 前端：纠错与生成笔记失败时，除了结果区高亮，还会**弹一个 toast**（`notify(msg,'error')`），不用去翻结果区
- `/ai/status` 的 `fallbackModel` 现在为空，一眼能看出"没有备用模型"
