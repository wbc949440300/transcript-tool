## 0. 一句话结论

核心链路整体可用：**306 项单测全过**；B站 / 快手 / 小红书 / 图片 OCR / 上传文件 / 监听目录 /
AI 纠错 / AI 笔记 / 5 种导出 / 批量 / 媒体代理 / 鉴权 / 页面路由 都实测通过。

但发现 **3 个高严重度真 bug + 1 个新机部署阻断项**：

1. **画面文字 OCR 的“近似帧去重”会把不同字幕帧合并，静默丢字**（合成视频实测整句丢失）。
2. **上传非 mp4 / 非浏览器容器视频后，预览/截图/保存全部 400**（HEVC `.mkv`、H.264 `.avi` 实测）。
3. **`/archive/file` 下载中文文件名归档时 500**（ASCII 名正常，中文名必现）。
4. **`requirements.txt` 缺 `python-multipart`，按 README 在新机安装后服务无法 import/启动**。

另有磁盘泄漏、启动预热阻塞、手机端结果页被导航遮住等中低风险问题，见 §3。

## 3. 确认的缺陷（按严重度）

### 3.1 【高】画面文字 OCR 近似帧去重会合并不同字幕帧，静默丢字

**位置**：`app/frame_ocr.py:108`（`_DUP_HAMMING = 8`）、`146-156`（连续帧分组、取组内最后一帧）、
`163-175`（跨组 dHash 复用）、`197`（复用 OCR 结果）、`247-248`、`360-362`（探针无字就跳过全扫）。

**原因**：16×16 dHash 对“静态背景 + 中央一行字幕”的画面不敏感，不同字幕的汉明距离只有 0~6，
低于阈值 8，被当成同一画面；每组只 OCR 最后一帧，其余帧直接复用该结果。
如果组内最后一帧正好是转场/空白/无字帧，整组文字直接丢失，探针还会误判“没有画面文字”并跳过全扫。

**实测证据（合成帧 + 本地视频）**：
- 720×1280、静态边框背景、90px 微软雅黑，4 帧不同字幕；帧间 hamming = **0 / 3 / 3**。
  `_ocr_frames()` 对 4 帧全部返回 **“第四句继续变化”**（只保留最后一帧）。
- 把最后一帧改成空白帧：4 帧全部返回空列表，**三条字幕全部丢失**。
- 合成 6s 视频（4 段字幕，每段 1.5s）跑 `extract_frame_text()`：只得到 2 条 block，
  **第一句“第一句字幕内容”完全丢失**。

**影响**：抖音/快手/小红书默认开启画面 OCR；监听目录任务也可开启。静态背景的口播字幕视频
会静默丢内容，且结果看起来“成功”。这是本轮改动引入的内容损失，优先级最高。

**建议**：不要把“画面哈希”当作“文字未变化”的充分条件。可选：
- 只对 hamming == 0 的完全相同帧去重；或
- 对字幕区域单独计算变化/直接逐帧 OCR 后按文本去重；或
- 将去重降级为可选加速项（环境变量），默认关闭；至少不要取“组内最后一帧”，改为取组内有字帧并保留多帧结果。

### 3.2 【高】上传视频转码后生成 `video_h264.mp4`，媒体接口只接受 `video.<ext>`，预览/截图/保存 400

**位置**：`app/file_transcribe.py:71-72`（输出名 `video_h264.mp4`）、`152-153`（`task.videoUrl = "file://" + kept_video.name`）；
`app/api.py:536`（`_serve_local_media` 正则 `video\.(mp4|webm|mkv|mov|m4v)`）。

**触发**：上传/监听目录导入 `.mov/.mkv/.m4v` 且编码为 HEVC 等浏览器不支持编码 →
`_ensure_browser_preview()` 转码为 `video_h264.mp4`；`videoUrl=file://video_h264.mp4`；
`/api/media/proxy` 正则不匹配，返回 400“参数不合法”。
同样，允许上传的 `.avi/.flv` 即使编码是 H.264 也不会转码，`videoUrl=file://video.avi|flv`，同样 400。

**实测证据**：
- 2s HEVC `.mkv`（任务 `7522943514933571023`）：SUCCESS，`videoUrl=file://video_h264.mp4`，
  `GET /prod-api/media/proxy?taskId=...` → **400 `{"code":500,"msg":"参数不合法"}`**。
- 1s H.264 `.avi`（任务 `7522943800240975269`）：SUCCESS，`videoUrl=file://video.avi`，
  同一接口 → **400**。

**影响**：这些格式上传后可以转写，但视频预览/截图/保存全部不可用；用户会看到“视频预览失败”。

**建议**：转码产物统一命名为 `video.mp4`；`_serve_local_media` 至少接受 `video*.(mp4|webm|mkv|mov|m4v|avi|flv)`；
同时把 `.avi/.flv` 无条件转封装为 mp4，避免容器兼容问题。

### 3.3 【高】`/archive/file` 下载中文文件名归档返回 500

**位置**：`app/api.py:334-339` `_file_response`；`app/api.py:402` `archive_file`。

**原因**：`Content-Disposition` 直接写入中文文件名；Starlette 用 latin-1 编码响应头，
`UnicodeEncodeError: 'latin-1' codec can't encode characters`。同项目的 note 下载已用 RFC5987，
archive 没走同一套。

**实测证据**：
- `GET /prod-api/archive/file?name=_tmp_ascii_test.txt` → **200**，`attachment; filename="_tmp_ascii_test.txt"`。
- `GET /prod-api/archive/file?name=2026-11-02_8EE6翻车…(4).txt` → **500 Internal Server Error**；
  `server_err.log` 栈顶为 `api.py:335` 的 `UnicodeEncodeError`。
- `/archive/content` 读同一文件正常（只 `/file` 下载失败）。

**影响**：任何外部脚本/Halo 插件通过该接口下载中文名归档都会失败；页面本身尚未接这个按钮。

**建议**：`_file_response` 统一改为 ASCII 兜底名 + `filename*=UTF-8''<percent-encoded>`（参考 `app/api.py:775`）。

### 3.4 【高｜部署】`requirements.txt` 缺 `python-multipart`，新机按 README 安装后无法启动

**位置**：`requirements.txt`（只有 9 个包）；`app/api.py:14,216,235` 使用 `File/Form/UploadFile`。

**证据/机制**：`starlette/formparsers.py` 在模块导入时 `import python_multipart`；
如果环境没有该包，`app.main` 直接 import 失败。`check_env.py` 的 `PKGS` 也没有检查它，
所以自检会显示“可以运行”，但 `python run.py` 会崩。
`dist/文案提取工具-v1.0.1.zip` 里的 `requirements.txt` 同样没有该包。

**影响**：新电脑/新容器按文档 `pip install -r requirements.txt` 后服务起不来；当前机器因环境里
恰好有 0.0.20 才能运行。

**建议**：`requirements.txt` 加 `python-multipart`；`check_env.py` 增加 `multipart` 检查；
发布包重新构建。

### 3.5 【中】文件转写在 `tmp_uploads/` 遗留 `.enh16k.wav`，长跑持续占磁盘

**位置**：`app/extractor.py:611-618`（`_enhance_audio` 生成 `src.with_suffix(".enh16k.wav")`）；
`app/file_transcribe.py:189-197`（finally 只删 `file_path`）；`app/history.py:134-163`（仅在启动时清理 >24h）。

**实测**：上传 `test_voice.wav`（任务 `7522938278790285217`）完成后，原上传文件被删除，
但 `tmp_uploads/7522938278790285217.enh16k.wav`（352,894 字节）仍在；`tmp_uploads` 里已有
10 个类似文件。16k 单声道 16-bit 约 **1.9MB/分钟**，30 分钟视频约 **57MB/条**。

**影响**：服务长期不重启时，上传/监听任务越多，临时目录越大；只有重启且文件超过 24h 才清。

**建议**：在 `_run_file_task` 的 finally 里同时删除 `file_path.with_suffix(".enh16k.wav")`；
或把增强音频放进 `tasks/<id>/` 随任务目录一起清理。

### 3.6 【中高｜代码审查】启动预热在全局 ASR 锁内下载/加载 medium，会阻塞首个文件任务

**位置**：`app/main.py:264-277`（启动即起 `model-warmup` 线程，加载 `TRANSCRIPT_WATCH_MODEL`）；
`app/extractor.py:373-396`（`_get_model` 在锁内，`WhisperModel` 构造可能联网下载）；
`app/extractor.py:542-543`（`_transcribe` 也要拿同一把 `_WHISPER_LOCK`）。

**触发**：新机首次启动、模型未缓存，用户立即上传文件（接口默认 `tiny`）；预热线程正在锁内下载
`medium`（约 1.5GB），文件任务在锁上等待，进度停在“准备转写”数分钟。即使模型已缓存，也要等
约 9 秒。预热没有环境变量可关，也不判断监听是否启用。

**建议**：预热不要占着转写锁做网络下载（先加载、再短临界区写缓存），或把预热做成可选；
至少不要在用户首个任务前强行下载 medium。

### 3.7 【中｜UI】手机端历史结果页自动滚动后，标题/工具栏被 sticky 导航遮住

**位置**：`static/index.html:17`（`.navbar{position:sticky;top:0;...}`）、`static/index.html:1819`
（`box.scrollIntoView({behavior:'smooth'})`）。

**实测（Playwright 390×844）**：`#vresult` 顶部 = -7.59，导航底部 = **149.14**，
结果标题 `8EE6翻车？…` 的 top=109.75、bottom=162.53 → 标题上半段被导航覆盖；
“导出下载 / AI 纠错 / 生成笔记”工具栏也在导航下方，首屏看不到。桌面 1440×900 导航高 59.4，
标题 top=69.6，可见——问题集中在手机端（导航换行后高 149px）。

**建议**：给结果容器加 `scroll-margin-top`（按实际 navbar 高度），或 `scrollIntoView` 后
`window.scrollBy(0, -navbarHeight)`；手机端也考虑压缩导航高度。

### 3.8 【低｜UI】风控冷却横幅重复显示

`app/alerts.py:119` 已生成“抖音 冷却中（约 X 分钟，验证码）”，`static/index.html:1559-1581`
又把 `/risk/status` 的逐平台冷却追加一遍，页面看到：
“抖音 冷却中（约 9 分钟，验证码）；抖音冷却中，约 9 分钟（验证码）。”
建议 alerts 已覆盖的平台就跳过逐平台项，或按 label 去重。

### 3.9 【低】`/watch/status` 把隐藏状态文件算成“待处理文件”

`app/watch_folder.py:491-504` 的 `_dir_usage` 统计目录下所有文件，包括
`.transcript_watch_state.json`。实测监听目录只有 `processed/` 和该状态文件，
页面仍显示 `inboxFiles=1 / inboxBytes=5259`。统计时应排除点文件和非媒体后缀。

### 3.10 【中高｜条件性｜代码审查】下载器代理自动接管未校验监听/证书，且用 `is_mitm` 忽略 `enable`

**位置**：`static/index.html:1852`（`proxyBad = !px.is_mitm`）、`1873`（按钮条件）、`1994`
（启动后仅在 `!px.is_mitm` 时自动调用 use-mitm）；`app/external_dl.py:1026-1043`
（`proxy_status` 有 `active_mitm`；`use_mitm_proxy` 只判断 Windows 就写系统代理）；
`app/external_dl.py:1118-1123`（`_restore_proxy` 用 `_proxy_set(0, sv)`，保留 ProxyServer 字符串）。

**风险**：
- `proxy_listening === false` 或证书未安装时，前端仍会自动把系统代理指向 `127.0.0.1:2023`，
  可能导致浏览器/微信代理连接失败或 HTTPS 证书错误；
- 停止下载器后 `ProxyEnable=0` 但 ProxyServer 仍指向 2023，`is_mitm` 仍为 true，
  页面不再显示“把系统代理指向本机”按钮，用户失去入口。
- 修改系统代理属于全局影响，测试时未实机触发；建议修完再做一次真实开关验证。

**建议**：前端用 `px.enable && px.is_mitm`（或后端 `active_mitm`）判断；自动接管前检查
`d.proxy_listening` 和 `d.cert_installed`；服务端 `use_mitm_proxy` 增加端口监听/证书校验；
`_restore_proxy` 还原时同时清空 ProxyServer 或恢复到备份值。

### 3.11 【低｜代码审查】无口播 + AI 纠错后导出会误标“口播文案”并重复追加原始 OCR

`app/export.py:120-133` 用 `text_content == frame_text` 判断正文是否来自画面；AI 纠错后
`corrected_text` 与原始 `frameText` 不再相等，导出 `corrected=1` 时标签变成“口播文案”，
同时 `frameMainText/frameSceneText` 又被追加，正文出现“纠错文本 + 原始 OCR”两份。
建议在提取时记录正文来源（`source=asr|frame`），不要事后比较文本。

### 3.12 其它 API 一致性 / 小问题

| 项 | 现象 | 说明 |
|---|---|---|
| `/media/proxy` 的 `index` 越界 | 实测 `index=99` 返回 **200**，实际取最后一条 URL | `app/api.py:527` 用了 `min(index, len-1)`；建议越界返回 400/404，避免静默播错流 |
| `/login/start`、`/login/check` 不支持平台 | HTTP **200** + body `code=500` | 与其它接口 4xx 语义不一致；建议 HTTP 400 |
| `/proxy/check` 文档 | `docs/扩展点与二次开发指南.md:19` 写 `GET`，实现是 `POST`（`app/api.py:998`） | GET 实测 404；改文档或加 GET |
| 账号登录状态 | `app/account_login.py:64-94` 按“任意一条未过期 cookie”判定已登录 | 登录态 token 过期但追踪 cookie 未过期时可能误报（疑似） |
