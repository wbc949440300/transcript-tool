## 0. 结论摘要

**能立刻修、且直接关系到风控的三件事（都是"静默失效"，HANDOFF 里没记）：**

1. `utils.throttle()` 里 `os` 未导入 → **全项目节流配置形同虚设**（实测：设 5000ms 仍只等 0.8s）。
2. `douyin.py` 缺 `import json` / `Path` → cookie 注入日志永远是"失败"（实际已生效），JSON 字幕分支死掉。
3. `extractor._pick_subtitle()` 形状判断错误 → 有 CC 的视频要么 **文案变成一串 URL**，要么**任务直接崩**（实测复现）。

**风控结构性缺口（不是 bug，是设计缺口）：**

| # | 缺口 | 现状 | 后果 |
|---|---|---|---|
| G1 | 无出口多样性 | 全程本机 IP，代码里**没有任何代理支持**（grep 无命中） | 一次标记 = 全平台连坐；账号池再多也共用一条 IP |
| G2 | 无并发/预算闸门 | 一个任务一个线程；批量是"每 3s 起一条"而不是"跑完再起" | N 条同时飞行；日配额无上限 |
| G3 | 只有抖音/快手有平台锁 | B站/小红书/YouTube 走 yt-dlp 路径，**无平台互斥** | 小红书批量 = 真并发打平台（历史上已触发 300011 限流） |
| G4 | 冷却判定过粗 | 抖音"没拿到 title/video_url"一律冷却 30 分钟 | 一次网络抖动 → 整平台停摆半小时（误伤，可用性问题） |
| G5 | 重试方向错了 | 失败后**升级为带 cookie** 重试 | 风控场景下"提高曝光"是最坏策略；账号被反复带到前台 |
| G6 | 无浏览器指纹策略 | 抖音走无痕 Chromium + 固定 UA，无 stealth 参数 | 与真实用户差异大，反爬成本低（当前仍能用 = 加固项） |

**最省事的现实结论：** 把 P0（第 3 节）修完 + 加一个"全局任务队列 + 平台日预算"，就能覆盖 80% 的风控暴露面，且不改架构。

## 1. 已实测的代码缺陷

### 1.1 `utils.throttle()` 的节流配置完全失效 ★高 [已实测]

`app/utils.py:362` 用了 `os.environ.get(...)`，但文件顶部只 `import os as _os`（第 44 行）→ `NameError` 被下层 `except Exception` 吞掉 → 永远走 `min_interval = 0.8`。

实测：
```
TRANSCRIPT_THROTTLE_MIN_MS=5000 → 第二次调用等待 0.802s（期望 5s）
```

影响：`TRANSCRIPT_THROTTLE_MIN_MS` 是**唯一的全局限速旋钮**（三条通道共用），现在无论设多少都是 0.8s。批量/多标签场景下等于没有刹车。HANDOFF §5.1 把它列为可配置项，实际是死配置。

### 1.2 `douyin.py` 缺两个导入 → 日志误导 + 字幕静默丢失 ★高 [已实测]

`app/douyin.py` 的 import 集合实测为：`Callable, Optional, _re, annotations, load_netscape_cookies, logging, mark_platform_cooldown, pick_account, platform_cooldown_enabled, platform_cooldown_remaining, platform_of, platform_serialized, re, sync_playwright, throttle, time, urllib, urlparse` —— **没有 `json`，没有 `Path`**。

两处后果：

- `app/douyin.py:157`：`ctx.add_cookies(cs)` 已生效，紧接着 `Path(ck).name` 抛 `NameError` → 被 `except` 捕获 → 日志写 **"抖音 cookie 注入失败: name 'Path' is not defined"**。cookie 其实注入成功了，但日志会让人以为没成功（HANDOFF §16.8"抖音一直匿名跑"的排查会被这条假日志带偏）。
- `app/douyin.py:70`：`_fetch_subtitle_text` 里 `json.loads(raw)` → `NameError` → 被内层 `except` 吞 → JSON 格式的自带字幕**永远返回空**，退回 ASR（多一次下载 + 转写，也多一次平台交互）。

同类"缺失导入"上一轮修过一次（`_host_of`），说明这批模块没有静态检查兜底。

### 1.3 `_pick_subtitle()` 平台字幕路径是坏的 ★高 [已实测]

`app/extractor.py:114-131`。实测三种形状：

| 输入 | 实测结果 | 应该 |
|---|---|---|
| `requested_subtitles: {zh-CN: {ext,url}}` | 返回 `'https://example.com/sub.srt?sign=abc'` | 返回字幕**正文** |
| `subtitles: {zh-CN: [{ext,url}]}` | **抛 AttributeError**（`'list' object has no attribute 'get'`） | 返回正文或空 |
| 只有 `automatic_captions` | 返回 `''`（字段根本没读） | 也应当读 |

根因两条：

1. `_extract_info` 用 `skip_download=True` → yt-dlp 的 `process_subtitles()` 只填 `url`/`ext`，**不会填 `data`**（我读了 site-packages 里 `yt_dlp/YoutubeDL.py` 的源码确认）。代码优先 `entry["data"]`，拿不到就取 `entry["url"]` 当文案 → **把字幕地址当成了口播文案**。
2. `info["subtitles"]` 的规范形状是 `{lang: [ {url,ext}, ... ]}`（值为 list），代码按 dict 调用 `.get()` → 崩。

另有一处 `break` 位置错误：某语言条目缺 `data`/`url` 时会直接跳出语言循环，不再试其他语言。

**触发条件**：平台提供 CC 的视频。已测过的 B站样片没有 CC，所以一直没暴露；YouTube 从未验证 —— 一旦用就是"文案变 URL"或"任务失败"，而失败信息会是原始的 `'list' object has no attribute 'get'`。

### 1.4 `archive.backfill()` 缺 `json` → 补档静默丢【画面文字】★中 [已实测]

`app/archive.py:102` 用 `json.loads`，模块没导入 `json` → `NameError` 被 `except Exception` 吞 → `extra = {}` → `frameText` 永远取不到。

后果：启动补档写出的 txt **不含【画面文字】段**，而任务成功时走的 `save_text_file()` 路径是含的（它走对象属性不走 JSON）—— 同一份历史，实时归档与启动补档产出不一致，且不报错、不告警。

### 1.5 冷却语义过粗：偶发失败 = 整平台停摆 30 分钟 ★中 [读码判定]

`app/douyin.py:248-252`：只要 `title` 与 `video_url` 都空，就 `mark_platform_cooldown("douyin", 1800)`，**不区分**：

- 真风控（页面返回验证/空壳）
- 网络超时（`timeout=35`，domcontentloaded + 轮询 35s，慢网会超）
- 链接失效/作品已删
- 页面结构改版导致拦截不到 `aweme/detail`

而冷却是对**整个平台**生效（`platform:douyin`），后续所有抖音任务在 30 分钟内直接快速失败。用户看到的是"风控冷却中"，真实原因可能只是一次超时 —— **误伤型可用性问题**（比真风控更常见）。

快手同样：`len(html) < 5000` 就判风控（`app/kuaishou.py:85`），移动端分享页改版/极短页面也会命中。

### 1.6 账号冷却惩罚错对象 ★中 [读码判定]

`app/extractor.py:88-89`：第二次尝试失败即 `mark_account_cooldown(pick_account(...), 900)`，**不看失败原因**。而 cookie 从第 3 次尝试才启用（`should_use_cookie` fallback 模式）—— 前两次失败与账号无关，却把账号关 15 分钟。批量跑一批失效链接，账号池会被自己关干净。

### 1.7 死代码 / 历史包袱（会误导后来人）★低 [已实测]

- `app/extractor.py:36 _whisper_device()` **定义了但无人调用**（全项目仅此处出现 `TRANSCRIPT_USE_CUDA`）；真实设备选择在 `_pick_device()`。HANDOFF §5.3 说它"由自动探测取代"，但函数还留着且注释描述的是旧行为。
- `_TASK_THREADS`（`extractor.py:33`）只 `add` 不 `discard`，长期持有可能已结束的 Thread 对象（量级小，但语义是错的）。

## 2. 平台提取链路的风控风险面

### 2.1 单任务请求量（按代码路径数出来的）[读码判定]

| 平台 | 页面/接口请求 | 媒体请求 | 最坏情况 |
|---|---|---|---|
| 抖音 | 1 次 headless 访问（真实浏览器会带几十个静态资源请求） | 1 次 CDN 直链 | 失败重试 → ×2（第二次带 cookie） |
| 快手 | 1 次 `m.gifshow.com/fw/photo/<id>` | 1 次直链 | 失败 → 专用通道 + 直链兜底 |
| B站/小红书/YouTube | yt-dlp `_extract_info` **最多 3 次**（第 3 次带 cookie） | 音频下载 `download_media` **最多 4 次** + 预览 `download_media` **2 次** 或 HLS 拉流 | **约 9 次平台请求 / 单条任务** |
| 小红书图文 | 1 次渲染 + 20 张图下载（`fetch_image`，**无任何节流**） | — | 21 次连续请求 |

一条失败的链接，会被放大成最多 9 次带重试的平台交互；而每次重试还会**换 UA**（`robust_media._UA_POOL` 随机 6 选 1）—— 同一账号/同一 IP 短时间内在平台侧表现为"多个不同浏览器来回访问同一个视频"，这本身就是异常信号。

### 2.2 并发模型（这是当前最大的风控隐患）[读码判定]

- `start_async()`：一个任务一个 `threading.Thread`，**无上限、无队列**（`extractor.py:925-934`）。
- 批量队列的"间隔"是**启动间隔**不是完成间隔：`batch.py:59-64` 起完一条立刻 `sleep(3s)` 就起下一条，而任务本身要 30~120 秒 → **N 条真的在同时跑**。
- 平台互斥锁只有抖音、快手有（`platform_serialized`）；**小红书/B站/YouTube 没有任何平台级互斥**，只有那个 0.8s 的同域节流。
- 结论：**批量 10 条小红书 ≈ 10 路并发打平台**。历史记录里 `300011 Account exception` 与"小红书当天就在限流"就是这条路走出来的。

### 2.3 身份与指纹 [读码判定 + 评估]

- **出口**：无代理支持。yt-dlp 的 opts 里没有 `proxy`、urllib 用默认 opener、Playwright 没有 `proxy=` → 所有平台、所有账号共用本机 IP。账号池轮换只换 cookie 不换 IP，风控侧一关联就是"同一台机器多个小号"。
- **指纹**：抖音通道 `p.chromium.launch(headless=True)` + 硬编码 UA `Chrome/120`，**没有** `--disable-blink-features=AutomationControlled`（只有 `browser.py` 那套有），每任务一个全新无痕实例（无历史、无插件、无语言/时区/分辨率抖动）。
- **登录态与抓取共环境**：小红书 cookie 来自 `cookies/_browser_profile`（`login_cookie.py` 用同一个 profile 登录），抓取时又用同一 IP 访问 —— 平台的"登录行为"与"机器式访问"可被关联到同一账号。
- **现状判断**：目前匿名优先 + 低频是有效策略（HANDOFF 记录的失败都发生在"批量/重试叠加"之后）。也就是说**当前不是"被拦了"，而是"离被拦还有多少余量"的问题**。

### 2.4 已经在做的、值得保留的部分

- 匿名优先、失败才带 cookie（`TRANSCRIPT_COOKIE_MODE=fallback`）
- cookie 按目标域过滤后才外发（`load_netscape_cookies` 的 `primary` 过滤 + `cookies_header_for` 的 host 匹配）
- 平台冷却持久化（`cookies/.cooldown.json`，重启仍生效）
- 账号池轮换 + 冷却跳过
- 媒体预览"不再二次请求平台"（`_ffmpeg_pull_hls` 复用首次提取的 m3u8）—— 这条是上一轮做的最正确的风控优化
- 抖音路径不再把 `caption` 当文案（少一次无谓的全片下载？不，是少一次错误结果）

### 2.5 风控之外的现实隐患（运维面）

- **系统代理副作用**：下载器运行时把系统代理改成 `127.0.0.1:2023`（MITM），服务启动会自动拉起它 → 只要服务在跑，全机流量走 MITM。备份/还原逻辑写得挺细（保留最早原始值、无备份时关代理兜底），但**没有"启动时体检残留"**：如果上次是硬关机/杀进程，且本次服务还没起来，用户上网就是坏的。
- **根证书**：SunnyNet CA 装进了系统根信任库。这是全机 TLS 信任面，工具一旦被替换/带毒，影响面是全机的（不是本项目可控范围，但要知道）。
- **凭据明文**：`.env`（LLM key）、`cookies/*.txt`、`cookies/_browser_profile/`（已登录浏览器 profile）都在项目目录里。
- **没有版本控制**：`transcript_tool` 不是 git 仓库（`git log` → fatal），只有 `.gitignore`。24 个模块、每天多次改，**无法回滚、无法对比、没有变更历史**。

## 3. 解决方案

### P0 · 今天就能改完（低风险、收益最大）

| # | 动作 | 落点 | 效果 |
|---|---|---|---|
| 1 | 修 `os` / `json` / `Path` 三处缺失导入 | `utils.py`、`archive.py`、`douyin.py` | 节流旋钮活了；假日志消失；JSON 字幕可用 |
| 2 | 重写 `_pick_subtitle()`：只认已下载的 `data`；`subtitles`/`automatic_captions` 按"list of dict"处理；**禁止把 URL 当文案**（拿到 URL 就再下一次或直接落到 ASR）；修 `break` | `extractor.py` | 有 CC 的视频不再出"URL 文案"/不崩 |
| 3 | 冷却语义拆三类：`risk`（403/429/验证码/空壳页）/ `transient`（超时、网络）/ `permanent`（已删、不支持）→ **只有 risk 冷却**；且冷却粒度从 `platform` 改为 `platform + 出口标识`（IP 或账号） | `douyin.py`、`kuaishou.py`、`utils.py` | 偶发失败不再停摆半小时 |
| 4 | 重试不再无脑升级 cookie：只在"需要登录态的特征"（401/登录墙/笔记不可浏览）才带 cookie；其余失败**退避后匿名重试**或直接失败 | `extractor._extract_info`、`_fetch_platform`、`robust_media` | 账号不再被无谓带到前台 |
| 5 | 节流参数实用化：默认间隔提到 **2~3s + 抖动**，并给"平台级最小间隔"（不只按域名） | `utils.throttle` | 立刻降低被判定机器行为的概率 |
| 6 | 前端接上已存在的 `GET /risk/status`（后端已实现，页面没用） | `static/index.html` | 冷却是可见的，用户能自己避让 |

### P1 · 结构性（1~3 天）

1. **全局任务队列**：改成"1 个调度器 + 每平台 1 个并发槽（跨平台可并行）"，替代"一任务一线程"。批量从此是"排队"而不是"并发"；顺带解决显存/内存峰值与"同一链接连点两次跑两遍"。
2. **请求预算账本**：`cookies/.budget.json` 记 `{平台: 当日请求数, 连续失败数, 最近 403/429 时间}`；超日配额或失败率阈值 → 自动熔断 N 分钟 + **半开探测**（放 1 条试探，成功才恢复）。把"冷却"从布尔量升级成状态机。
3. **代理支持**：加 `TRANSCRIPT_PROXY_<PLATFORM>` / `TRANSCRIPT_PROXY_POOL`，贯通三处（yt-dlp `proxy=`、urllib opener、Playwright `proxy=`）。允许"页面请求走代理 A、CDN 媒体直连"（媒体往往不校验 IP，省钱）。账号与出口绑定后，账号池才有真实意义。
4. **指纹统一**：抖音通道并入 `browser.py` 的持久 profile 机制（每账号一个 profile 目录 + stealth 参数 + 真实 UA/语言/时区），替掉"无痕 Chromium + 固定 UA"。
5. **人机校验识别与停机**：命中滑块/验证码特征时**立刻停手并告警**，不重试（HANDOFF 已记录"停手等衰减才是恢复最快的路"，把它落成代码）。

### P2 · 中期 / 与路线图合并

- 三条通道抽象成**平台适配器**（声明：是否需要登录、请求预算、退避策略、指纹策略、风控识别规则）—— 这正是 HANDOFF 里"未来 Go 插件化"的前置工作，先在 Python 侧把接口定下来，迁移时就是抄结构。
- 图文笔记（小红书）改成"只 OCR 前 N 张 + 后续按需"，减少 20 连击。
- 加 `pytest` 的最小测试集：**优先覆盖风控策略纯函数**（冷却判定、预算扣减、退避计算、字幕形状解析）—— 这类"参数敏感但没人会手工回归"的逻辑最该有单测。
- 保留策略统一：现在 DB 只留 20 条，而 `文案输出/` 是无限归档（两套真相）。建议 DB 改按**天数**保留 + 只对"含本地预览视频"的记录做文件清理；归档 txt 作为长期真相单独管理。

### 不建议做的

- ❌ 换 UA/加代理去"冲"被限流的账号（提高曝光 = 加深标记）。
- ❌ 为了成功率把 `TRANSCRIPT_COOKIE_MODE` 设成 `always`（等于全程暴露账号）。
- ❌ 保留"失败就带 cookie 重试"作为默认策略。
- ❌ 给抖音通道加"多档重试抢占"（当前 1 次访问已经够用，重试只会放大暴露）。

### 6.4 本轮新增的两个坑（已修）

1. **弹幕 ≠ 字幕**：B站 `subtitles` 只有 `danmaku`（XML + raw deflate）→ 必须按语言键过滤 +
   下载后做文本校验，否则乱码会被当文案写库。
2. **函数内局部 import 遮蔽模块级名字**：`_run_task()` 里原本有一句
   `from .robust_media import _referer_for`，导致函数前半段用 `_referer_for` 直接
   `UnboundLocalError`（真实任务失败一次才发现）。已删掉局部 import，并加了一条静态扫描
   （"局部 import 出现在同名使用之后"）确认全项目无同类问题。
