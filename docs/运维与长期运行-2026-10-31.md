### ③ 持久队列（`app/scheduler.py`）

**问题**：队列在内存，服务一重启排队中的任务就没了。

**做法**：
- 排队 / 运行中的任务落盘到 `queue_state.json`（原子写：唯一 tmp 名 + 专用锁 + 重试，
  避开 Windows 上 rename 偶发 WinError 32）
- `submit()` 入队即落盘；worker 取走时标 `running`；跑完从文件里移除
- 服务启动时 `scheduler.restore()`：把文件里的任务重新入队（**运行中被重启打断的也会重跑**——
  ASR 结果本来就没落库，重跑比悄悄丢掉更符合预期）
- 文件路径可用 `TRANSCRIPT_QUEUE_FILE` 改；已加入 `.gitignore`

**实测**：入队后文件里有该任务（state=running）→ 跑完文件清空；重启恢复路径有单测覆盖。

### ④ 本地告警（`app/alerts.py`）

**问题**：只有 `/risk/status` 和日志，失败率/积压/磁盘没有主动提醒。

**做法**（不依赖任何外部服务）：
- 四类检查：**磁盘余量**、**失败率**、**队列积压**、**平台冷却**
- 两条出口：写 `app.log`（**内容没变不重复写**，靠签名比对）+ `/risk/status` 的 `alerts` 字段
- 后台巡检线程（默认 5 分钟，`TRANSCRIPT_ALERT_INTERVAL=0` 可关）
- 页面顶部横幅会显示 `⚠ …`；`danger` 级（磁盘）变红色样式

| 阈值变量 | 默认 |
|---|---|
| `TRANSCRIPT_ALERT_FAIL_RATE` | 0.5 |
| `TRANSCRIPT_ALERT_TASKS` / `_MIN_TASKS` | 20 / 5 |
| `TRANSCRIPT_ALERT_QUEUE` | 20 |
| `TRANSCRIPT_ALERT_DISK_GB` | 2.0 |

### ⑥ 看门狗（`scripts/watchdog.py`）

**问题**：进程崩了不会自己起来。

**做法**：
- `_alive(port)`：TCP 能连上就算活（不依赖 API token，探活不需要凭据）
- 挂了就用与手工重启一致的方式拉起（PowerShell Start-Process，隐藏窗口 + server.log）
- 支持 `--once`（放计划任务）/ 常驻循环 / `--dry-run`（只报告不启动）
- 日志落 `watchdog.log`，**只在状态变化时写**，不刷屏

**注册成计划任务（已完成，2026-10-31 15:52 注册并实测）**：

- 任务名：`文案提取-看门狗`
- 频率：每 5 分钟；只在使用交互方式（登录状态下运行）
- 执行：`F:\python\pythonw.exe "F:\文案提取工具\transcript_tool\scripts\watchdog.py" --once`
  （**pythonw** = 无控制台；脚本在 `sys.stdout is None` 时不加 StreamHandler，所以不会报错刷屏）

**实测（真杀真拉）**：
1. 服务在线时跑一次 → 上次结果 `0`，什么都没做、无窗口、静默 ✅
2. `taskkill` 掉服务 → 触发任务 → **8 秒内自动拉起**，新进程是 `pythonw.exe`，`/prod-api/health` 正常 ✅

**删除**：`schtasks /delete /tn "文案提取-看门狗" /f`

> ⚠️ **两个注册踩坑（都踩过）**：
> 1. `schtasks /create /tr "…工具\transcript_tool…"` 会把路径里的 `\t` 当成**制表符** →
>    任务存进去就跑不起来（上次结果 `2` = 文件找不到）。改用 PowerShell 的
>    `New-ScheduledTaskAction` + `Register-ScheduledTask`（不走那个字符串解析）才正确。
> 2. 用脚本生成 .ps1 时，**别在源码里写 `\\` 转义**（外层工具可能把它折成单个 `\`，
>    于是 `\t` 又变制表符）——改为**动态拼路径**（`os.sep` 拼接）再嵌进脚本。
>
> 验证方式：`(Get-ScheduledTask -TaskName '文案提取-看门狗').Actions | fl *` 看 `Execute/Arguments`
> 里有没有 TAB，或 `schtasks /query /tn … /v /fo LIST` 看"上次结果"是否为 0。

### 3. 浸泡脚本 `scripts/soak.py`

**只走本地文件上传**，不发任何平台请求 —— 不消耗每日额度、不触发风控，
专门验证"连续跑很久会不会涨内存/堆垃圾"。

```
python scripts/soak.py --minutes 60                    # 跑 60 分钟
python scripts/soak.py --rounds 5 --files-per-round 2  # 或按轮次
python scripts/soak.py --minutes 5 --clip-seconds 8 --model tiny   # 快速自检
```

每轮：生成/上传若干音频 → 等转写完成 → 采样 **服务进程 RSS / 历史条数 / tasks 与 cookies 体积 / 磁盘余量 / 告警数**，
逐轮写 `soak_report.jsonl`，结束时打印"首轮→末轮"的增量汇总。

**短跑自检**（2 轮 × 2 个 8 秒音频，tiny）：

```
第 1 轮 12.2s | RSS 657.9MB | 历史 19 条 | tasks 146.1MB | 磁盘余 350.8GB
第 2 轮  6.1s | RSS 659.3MB | 历史 20 条 | tasks 146.1MB | 磁盘余 350.8GB
汇总：RSS +1.4MB，磁盘/目录体积无增长
```

### 5. ASR 批处理提速（⑦ 的软件半边）——已实现，**默认关闭**

- 新增 `_asr_batch_size()`（`TRANSCRIPT_ASR_BATCH`，**默认 0 = 关**）与 `_transcribe_stream()`
- 开启时用 faster-whisper 的 `BatchedInferencePipeline`，并带 `word_timestamps` +
  `_split_long_segments()` 把批处理产生的长段按词级时间戳切回正常粒度
  （`TRANSCRIPT_SEG_MAX_SEC`，默认 8 秒，硬上限 1.5 倍）
- 任何异常（老版本、显存不够）自动回落逐段推理，**不会让任务失败**

#### 实测（469 秒 / 7.8 分钟真实音频，small 模型，RTX 3050 6GB）

| | 耗时 | 字数（去空白） | 段数 | 平均段长 | 最长段 |
|---|---|---|---|---|---|
| 顺序推理（现状） | 47.5s | 3044 | **281** | 1.7s | — |
| 批处理 + 词级切分 | **13.9s（3.42x）** | 2994 | 55 | 7.9s | 15.4s |

内容对比（同一条音频）：

| 指标 | 结果 |
|---|---|
| 去空白后相似度 | 0.850 |
| **再去标点后相似度** | **0.888** |
| 去标点后字数 | 3041（顺序） vs 2772（批处理）→ **少 8.8%** |
| 差异形态 | 丢的是短衬词（如"要的"整段消失），不是整句错乱 |

**6GB 显存压力**：`medium + batch=8` 在 15 秒片子上跑通（4.7 秒，无 OOM）——
所以显存不是障碍，**质量差异才是**。

#### 为什么默认关

1. ASR 文本正是这个项目最在意的产出（用户反馈过"提取的文字不行"），
   批处理会稳定地丢掉约 9% 的字（多为衬词），这个代价不该由默认路径承担
2. 顺序推理是此前全部验证（SRT、双 ASR、时间戳、术语）所基于的路径
3. 想要吞吐时一条 env 就能开，且 OOM 会自动回落

> 建议：**跑量/上云时**再开（那时显存富余、且通常不需要逐句字幕）。

### 1. 告警外部推送（已接通 Server酱）

两条通道任选其一，都走**直连**（不读系统代理，免得被视频号下载器的 MITM 绕进去）：

| 通道 | 配置 | 协议 |
|---|---|---|
| **Server酱 → 微信**（当前在用） | `TRANSCRIPT_ALERT_SERVERCHAN_KEY=<SendKey>` | **表单** POST `https://sctapi.ftqq.com/<key>.send`（`title`/`desp`）；主机可用 `TRANSCRIPT_ALERT_SERVERCHAN_URL` 覆盖 |
| 企业微信 / 钉钉 / 飞书 | `TRANSCRIPT_ALERT_WEBHOOK=<url>`（+可选 `TRANSCRIPT_ALERT_WEBHOOK_BODY`） | JSON POST；默认体 `{"msgtype":"text","text":{"content":"…"}}` = 企微/钉钉直接可用；飞书用 `{"msg_type":"text","content":{"text":"{msg}"}}` |

共同规则：只在**告警内容变化**时推、5 分钟内最多一条、失败只记日志、没配就静默跳过。
**回执校验**：HTTP 2xx **且**（若回 JSON）`code` / `errcode` / `errno` 为 0 才算成功。

**实测**：真实推了一条（`.env` 里已配 SendKey，返回 True，微信收到）；
单测覆盖 9 种情况（Server酱成功/被拒、企微 errcode 非 0、限流、未配置、不可达、引号转义…）。
另外**顺手抓到一个测试卫生问题**：`.env` 里的真 key 会被测试进程读到 → 已在 `conftest.py` 里
把告警通道全部关掉（`SERVERCHAN_KEY=""`、`WEBHOOK=""`、`NOTIFY=0`），**测试绝不会真往微信推消息**。

### 2. 云上可跑改造

#### 2.1 启动逻辑抽出来并跨平台化

原来 `run.py` 里内联了"内置 ffmpeg 前置 PATH + `os.add_dll_directory`"，
而 `os.add_dll_directory` **只有 Windows 有** —— 云端 Linux 起服务会直接 AttributeError。

现在抽成 `app.env.prepare_runtime_env(root=None)`：
- 用 `getattr(os, "add_dll_directory", None)` 探测，没有就跳过
- 顺带把 HF 镜像默认值也放进来（用户显式设置过则不覆盖）
- 可单测（4 项：内置 ffmpeg 优先级、**删掉 add_dll_directory 仍能跑**、无 tools 目录、不覆盖用户设置）

#### 2.2 视频号下载器的降级守卫

`app/external_dl.py` 新增 `IS_WINDOWS`，五个入口全部守卫：

| 入口 | 非 Windows 行为 |
|---|---|
| `probe()` | 返回 `platform_supported: False` + "仅支持 Windows；云端请把视频同步到监听目录"（不探测、不报错） |
| `install()` / `start()` | 返回带 `error` 的失败字典（不抛异常） |
| `stop()` | 返回 `stopped: True, already: True`（云端本来就没有这个进程，退出钩子不会误报） |
| `_proc_running()` | 直接 False（不再调用 tasklist） |

**验证**：6 项测试（含"IS_WINDOWS=True 时不能误伤正常路径"）。

#### 2.3 建议的分工（视频号）

```
本机（Windows）                         云端（Linux）
微信 + MITM 下载器  →  下载目录  ──同步──→  监听目录  →  本服务转写 → 归档/历史
（点一次下载）          （微信里手动这一步无法自动化，是平台限制，不是代码问题）
```

其余平台（抖音/快手/小红书/B站）与本地文件上传都可以直接在云端跑。

#### 2.4 如实说明：没做到的

- `login_cookie.py` 依赖本机浏览器内核（Edge/Chrome），云端要自己装 chromium
- `scripts/setup_new_machine.py`（一键装环境）是 Windows 导向的
- **Linux 上并没有真机跑过**，只做了守卫层的单测；真正上云前建议先在那台机器上
  `python run.py` 起一次、跑一条 B站/本地上传任务验证

### 1. 视频号元数据：标题/作者/封面（`app/video_channel.py`）

视频流仍然拿不到（只有微信客户端能播），但**元数据**有公开预览接口可用：

```
POST https://channels.weixin.qq.com/finder-preview/api/feed/get_feed_info
body {"baseReq":{"generalToken":""},"shortUri":"<id>"}
```

做的事情：

1. 用户贴视频号链接时，不再只丢一句"不能解析"——顺带取回**标题/作者/封面**，
   写进提示里给他看，并**记下来**
2. 文件经下载器落到监听目录后，按文件名与新记的标题做匹配（完全一致，或两边都 ≥6 字的包含关系），
   命中就把任务标题/作者/封面换成真的 —— **不再是文件名当标题**
3. 取不到就安静放弃，不影响主流程；响应解析用容错遍历（字段名换过几版）

| 配置 | 说明 |
|---|---|
| `TRANSCRIPT_VC_META` | 记住元数据的文件（默认 `video_channel_meta.json`），只留最近 30 条 |

> ⚠️ **未验证**：手上没有真实的视频号分享链接，`get_feed_info` 的**真实响应结构**没有实测过；
> 解析是容错的（`desc/title/nickname/coverUrl/...`），但字段名要不要调整得拿真链接试一次。
> 链接→shortUri 的解析、记忆/匹配、监听目录应用这三段都有单测覆盖。

### 2. 监听目录重复下载去重（`app/watch_folder.py`）

视频号同一条作品常被下载多次（下载器重试、误点两次），以前会**重复转写**。

- 指纹 = **文件大小 + 时长**（不做全文件哈希：几百 MB 哈希一次要几分钟）
- 命中已转写过的指纹 → 跳过转写、记一条 `skipped_duplicate`、文件移进 `processed/`
- 记录存 `watch_dedupe.json`（只留最近 300 条）

| 配置 | 默认 | 说明 |
|---|---|---|
| `TRANSCRIPT_WATCH_DEDUPE` | 1 | 设 0 关掉去重 |
| `TRANSCRIPT_WATCH_DEDUPE_FILE` | `watch_dedupe.json` | 指纹库路径 |

**实测**：同一份视频用两个文件名先后丢进监听目录 →
第 1 个建任务（`task 7522170541907759508`），第 2 个日志写明
"监听目录跳过重复文件（内容同 task …，不再重复转写）"，`/watch/status` 显示 `processed=1 / skipped_duplicate=1` ✅

### 3. 长视频转写进度（`extractor._transcribe` / `file_transcribe`）
